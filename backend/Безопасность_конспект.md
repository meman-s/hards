# Безопасность: инъекции, пароли, HTTPS/TLS

## 1. Защита от инъекций

**Инъекция** — внедрение в приложение произвольных данных (кода или команд), которые интерпретируются как часть запроса, запроса к БД или разметки. Цель атакующего — выполнить свой код, прочитать или изменить данные, получить доступ к системе.

### 1.1 SQL-инъекции

**Суть:** в параметры запроса (логин, поиск, фильтры) подставляют фрагменты SQL. Если строка склеивается с запросом без экранирования, злоумышленник может дописать свой SQL.

**Пример уязвимого кода:**

```python
query = f"SELECT * FROM users WHERE login = '{login}' AND password = '{password}'"
```

Подстановка `login = "admin' OR '1'='1"` даёт условие, которое всегда истинно, и может открыть доступ без пароля.

**Защита:**

- **Параметризованные запросы (prepared statements):** передавать пользовательский ввод только как параметры, никогда не вставлять в строку запроса. СУБД сама различает данные и структуру запроса.

```python
cursor.execute("SELECT * FROM users WHERE login = %s AND password = %s", (login, password))
```

- **ORM (SQLAlchemy и т.п.):** запросы строятся через API, подстановка идёт через параметры. Прямая конкатенация в ORM не используется.

```python
db.query(User).filter(User.login == login, User.password == hashed_password).first()
```

- **Валидация и ограничение ввода:** проверять формат (например, логин — буквы/цифры), длину, запрещать символы вроде `'`, `"`, `--`, `;`. Это дополнительный слой, но не замена параметризации.

**Итог:** основная мера — всегда использовать параметризованные запросы или ORM; ни при каких условиях не склеивать пользовательский ввод с SQL-строкой.

### 1.2 Инъекции в команды ОС (Command Injection)

**Суть:** пользовательский ввод попадает в команду оболочки (`os.system`, `subprocess.run` с `shell=True`, `eval` от строки). Злоумышленник может подставить `;`, `|`, `$(...)`, `&&` и выполнить свою команду.

**Защита:**

- Не передавать пользовательский ввод в shell. Вызывать программу через список аргументов без shell: `subprocess.run(["program", user_input], shell=False)`. Для путей и имён файлов — проверять на допустимые символы, использовать whitelist.
- Избегать `eval()` и `exec()` от пользовательских данных. Если нужна динамика — безопасные альтернативы (например, парсер конкретного подмножества выражений).

### 1.3 XSS (Cross-Site Scripting)

**Суть:** в страницу подставляется вредоносный JavaScript (через форму, URL, хранимые данные). Код выполняется в браузере жертвы — кража cookie, сессии, подмена страницы.

**Защита:**

- **Экранирование при выводе:** все данные от пользователя и из БД при выводе в HTML экранировать (например, заменять `<`, `>`, `"`, `'`, `&` на сущности). Шаблонизаторы (Jinja2, React и т.д.) по умолчанию экранируют, если не отключать «сырой» вывод.
- **Content Security Policy (CSP):** заголовок, ограничивающий источники скриптов и стилей, уменьшает последствия даже при появлении XSS.
- **HttpOnly и Secure для cookie:** сессионный cookie недоступен из JS и не уходит по HTTP — сложнее украсть через XSS.

## 2. Безопасное хранение паролей (hashing, salting)

Пароли не должны храниться в открытом виде. При утечке БД злоумышленник не должен получить пароли в читаемом виде. Задача — проверить введённый пароль, не зная его сам пароль.

### 2.1 Хеширование, не шифрование

- **Шифрование** — обратимо: есть ключ, можно расшифровать. Для паролей это плохо: ключ и данные вместе дают пароли в открытом виде.
- **Хеширование** — односторонняя функция: по паролю получаем фиксированной длины строку (хеш), по хешу восстановить пароль нельзя. При входе хешируем введённый пароль и сравниваем с сохранённым хешем.

Использовать нужно именно криптостойкие хеш-функции, рассчитанные на пароли: **bcrypt**, **scrypt**, **Argon2**. Обычный **MD5** или **SHA-256** без соли и без множества итераций — слабая защита от перебора.

### 2.2 Соль (salt)

**Соль** — случайная строка, уникальная для каждого пароля, которая добавляется к паролю перед хешированием. Хранится рядом с хешем (часто в той же строке).

**Зачем:**

- Одинаковые пароли дают разные хеши у разных пользователей — нельзя по одной таблице хешей массово подбирать пароли.
- Усложняет предвычисленные таблицы (rainbow tables): для каждой соли нужна своя таблица.

**Правила:** соль должна быть криптостойко случайной (например, `secrets.token_bytes(16)`), храниться вместе с хешем, не быть секретом.

### 2.3 Алгоритмы и пример (Python)

- **bcrypt** — адаптивный: можно увеличивать cost (число раундов), замедляет перебор. Широко используется.
- **Argon2** — победитель Password Hashing Competition, учитывает память и CPU, рекомендуется для новых систем.

**Пример с bcrypt (Python):**

```python
import bcrypt

password = b"user_password"
salt = bcrypt.gensalt(rounds=12)
hashed = bcrypt.hashpw(password, salt)

if bcrypt.checkpw(b"user_password", hashed):
    pass
```

**Пример с passlib (bcrypt под капотом):**

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto", bcrypt__rounds=12)
hashed = pwd_context.hash("password")
pwd_context.verify("password", hashed)
```

При регистрации: хешируем пароль (библиотека сама генерирует соль), сохраняем только хеш. При входе: хешируем введённый пароль с той же солью (она в сохранённом хеше) и сравниваем.

### 2.4 Чего не делать

- Не хранить пароли в открытом виде или в «обратимом» виде с общим ключом.
- Не использовать MD5/SHA1 для паролей без соли и без тысяч итераций (лучше вообще не использовать для паролей).
- Не использовать одну общую соль для всех пользователей.
- Не делать слишком малый cost (rounds): это ускоряет перебор.

## 3. HTTPS, TLS/SSL

### 3.1 Зачем нужен HTTPS

**HTTP** — трафик между браузером и сервером передаётся в открытом виде. Перехват (сеть, Wi‑Fi, провайдер) даёт доступ к паролям, cookie, телу запросов и ответов.

**HTTPS** — HTTP поверх криптографического протокола **TLS** (ранее использовали **SSL**, сейчас актуален именно TLS). Данные шифруются; перехватчик видит только факт соединения и домен, но не содержимое.

**Что даёт HTTPS:**

- Конфиденциальность: данные зашифрованы.
- Целостность: изменение данных в пути обнаруживается.
- Аутентификация сервера: клиент убеждается, что общается с нужным сервером (через сертификат).

Без HTTPS пароли, токены и cookie при логине можно перехватить. Современные стандарты (PCI DSS, GDPR, рекомендации браузеров) предполагают HTTPS для всего веба.

### 3.2 TLS/SSL кратко

- **SSL (Secure Sockets Layer)** — устаревший протокол, есть уязвимости. Не использовать.
- **TLS (Transport Layer Security)** — современная версия (1.2, 1.3). Обеспечивает согласование алгоритмов, обмен ключами и шифрование трафика.

**Роль в HTTPS:** перед обменом HTTP-данными клиент и сервер проводят **TLS handshake**: согласовывают версию TLS, шифры, сервер предъявляет сертификат, проверяется подлинность, формируется общий ключ. Дальше весь трафик шифруется симметричным шифрованием.

### 3.3 Сертификаты

**Сертификат** — электронный документ, связывающий домен (и при необходимости организацию) с публичным ключом. Подписан центром сертификации (CA). Браузер доверяет предустановленным CA и проверяет подпись и срок действия сертификата.

- **Самоподписанный сертификат** — для разработки; браузер покажет предупреждение, т.к. такой сертификат не подписан доверенным CA.
- **Продакшен:** сертификат от публичного CA (Let's Encrypt, коммерческие CA). Let's Encrypt выдаёт бесплатные сертификаты, часто автоматически (например, через Certbot).

### 3.4 Практика

- В продакшене весь трафик только по HTTPS. HTTP редирект на HTTPS.
- Cookie с флагом **Secure** — отправляются только по HTTPS.
- **HSTS (Strict-Transport-Security)** — заголовок, предписывающий браузеру всегда обращаться к сайту по HTTPS, уменьшает риск downgrade-атак и случайного перехода на HTTP.
- Сертификаты имеют срок действия; нужен процесс обновления (например, автоматическое обновление Let's Encrypt).

**Итог:** HTTPS с актуальным TLS и валидным сертификатом — обязательная база для защиты данных в веб-приложениях.
