# Nginx: Схемы и концепции

## 1. Что такое Reverse Proxy?

### Обычный Proxy (Forward Proxy)
```
Клиент → Proxy → Интернет → Сервер
         (скрывает клиента)
```

**Пример:** Прокси-сервер в офисе, через который все выходят в интернет.

### Reverse Proxy (Обратный прокси)
```
Клиент → Интернет → Reverse Proxy → Backend Сервер
                      (скрывает сервер)
```

**Пример:** Nginx принимает запросы и перенаправляет их на внутренние серверы.

### Визуальная схема Reverse Proxy

```
┌─────────┐
│ Клиент  │
│ (Браузер)│
└────┬────┘
     │ HTTP запрос
     │ GET /api/users
     ▼
┌─────────────────┐
│   Nginx          │  ← Порт 80 (публичный)
│   (Reverse Proxy)│
└────┬─────────────┘
     │ Проксирует запрос
     │ с заголовками
     ▼
┌─────────────────┐
│  FastAPI App    │  ← Порт 8000 (внутренний)
│  localhost:8000  │
└─────────────────┘
```

**Что происходит:**
1. Клиент отправляет запрос на `http://example.com/api/users`
2. Nginx получает запрос на порту 80
3. Nginx проксирует запрос на `http://localhost:8000/api/users`
4. FastAPI обрабатывает запрос
5. Ответ идёт обратно через Nginx к клиенту

## 2. Зачем нужен Reverse Proxy?

### Преимущества

```
┌─────────────────────────────────────────┐
│ 1. Скрытие внутренней структуры         │
│    Клиент не знает, что за Nginx        │
│    скрывается приложение на порту 8000  │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ 2. SSL/TLS терминация                   │
│    Nginx обрабатывает HTTPS,            │
│    а приложение работает по HTTP        │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ 3. Кэширование                          │
│    Nginx может кэшировать ответы,       │
│    не обращаясь к приложению            │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ 4. Сжатие (Gzip/Brotli)                 │
│    Nginx сжимает ответы перед отправкой │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ 5. Обработка статических файлов         │
│    CSS, JS, изображения отдаются        │
│    напрямую из Nginx (быстрее)          │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ 6. Rate Limiting                        │
│    Защита от DDoS и злоупотреблений    │
└─────────────────────────────────────────┘
```

## 3. Load Balancing - Концепция

### Проблема без Load Balancing

```
┌─────────┐
│ Клиент 1│────────┐
└─────────┘        │
                  ▼
┌─────────┐    ┌──────────────┐
│ Клиент 2│───▶│   Сервер 1   │  ← Перегружен!
└─────────┘    │  (8000)      │
               └──────────────┘
┌─────────┐
│ Клиент 3│────────┐
└─────────┘        │
                  ▼
               ┌──────────────┐
               │   Сервер 2   │  ← Не используется
               │  (8001)      │
               └──────────────┘
```

### Решение с Load Balancing

```
┌─────────┐
│ Клиент 1│────────┐
└─────────┘        │
                  ▼
┌─────────┐    ┌──────────────┐    ┌──────────────┐
│ Клиент 2│───▶│   Nginx      │───▶│   Сервер 1   │
└─────────┘    │ Load Balancer│    │  (8000)      │
               └───────┬───────┘    └──────────────┘
┌─────────┐           │
│ Клиент 3│───────────┼───────────▶┌──────────────┐
└─────────┘           │            │   Сервер 2   │
                      │            │  (8001)      │
                      └───────────▶└──────────────┘
                                  ┌──────────────┐
                                  │   Сервер 3   │
                                  │  (8002)      │
                                  └──────────────┘
```

**Преимущества:**
- ✅ Распределение нагрузки
- ✅ Отказоустойчивость
- ✅ Масштабируемость

## 4. Методы Load Balancing

### Round Robin (По кругу)

```
Запрос 1 → Сервер 1 (8000)
Запрос 2 → Сервер 2 (8001)
Запрос 3 → Сервер 3 (8002)
Запрос 4 → Сервер 1 (8000)  ← Цикл повторяется
Запрос 5 → Сервер 2 (8001)
```

**Когда использовать:**
- Все серверы одинаковой мощности
- Запросы обрабатываются примерно одинаковое время

### Weighted Round Robin (С весами)

```
Запрос 1 → Сервер 1 (weight=3) ─┐
Запрос 2 → Сервер 1 (weight=3) ─┤
Запрос 3 → Сервер 1 (weight=3) ─┘
Запрос 4 → Сервер 2 (weight=2) ─┐
Запрос 5 → Сервер 2 (weight=2) ─┘
Запрос 6 → Сервер 3 (weight=1)
```

**Когда использовать:**
- Серверы разной мощности
- Нужно отдать больше нагрузки мощному серверу

### Least Connections (Наименьшее количество соединений)

```
Сервер 1: 5 активных соединений
Сервер 2: 2 активных соединения  ← Выбирается
Сервер 3: 8 активных соединений

Новый запрос → Сервер 2 (меньше всего соединений)
```

**Когда использовать:**
- Запросы обрабатываются разное время
- Нужна более равномерная нагрузка

### IP Hash (Привязка к IP)

```
IP 192.168.1.10 → Всегда Сервер 1
IP 192.168.1.11 → Всегда Сервер 2
IP 192.168.1.12 → Всегда Сервер 3
```

**Когда использовать:**
- Нужна привязка сессий к серверу
- Кэширование на сервере (не в Redis)

## 5. Health Checks - Как это работает

### Без Health Checks

```
┌─────────┐
│ Клиент  │
└────┬────┘
     │
     ▼
┌──────────────┐    ┌──────────────┐
│   Nginx      │───▶│   Сервер 1   │  ← Упал!
│              │    │  (8000)      │
│              │    └──────────────┘
│              │
│              │    ┌──────────────┐
│              │───▶│   Сервер 2   │  ← Работает
│              │    │  (8001)      │
│              │    └──────────────┘
└──────────────┘
```

**Проблема:** Nginx продолжает отправлять запросы на упавший сервер → 502 ошибки

### С Health Checks

```
┌─────────┐
│ Клиент  │
└────┬────┘
     │
     ▼
┌──────────────┐    ┌──────────────┐
│   Nginx      │    │   Сервер 1   │  ← Упал!
│              │    │  (8000)      │  ← Исключён
│ Health Check │    └──────────────┘
│              │
│              │    ┌──────────────┐
│              │───▶│   Сервер 2   │  ← Работает
│              │    │  (8001)      │
│              │    └──────────────┘
└──────────────┘
```

**Как работает:**
1. Nginx отправляет запрос на сервер
2. Если сервер не отвечает → увеличивается счётчик ошибок
3. После `max_fails` ошибок → сервер временно исключается
4. Через `fail_timeout` → Nginx пробует снова использовать сервер

## 8. Поток запроса через Nginx

### Детальный поток

```
1. Клиент отправляет запрос
   GET /api/users HTTP/1.1
   Host: example.com
   │
   ▼
2. Nginx получает запрос
   - Проверяет конфигурацию
   - Определяет location блок
   - Проверяет rate limits
   │
   ▼
3. Если статический файл
   /static/style.css
   → Отдаёт напрямую из файловой системы
   │
   ▼
4. Если API запрос
   /api/users
   → Выбирает сервер из upstream (load balancing)
   │
   ▼
5. Проксирует запрос к backend
   GET /api/users HTTP/1.1
   Host: example.com
   X-Real-IP: 192.168.1.10
   X-Forwarded-For: 192.168.1.10
   X-Forwarded-Proto: https
   │
   ▼
6. Backend обрабатывает запрос
   FastAPI → Database → Response
   │
   ▼
7. Backend отправляет ответ
   HTTP/1.1 200 OK
   {"users": [...]}
   │
   ▼
8. Nginx получает ответ
   - Может кэшировать
   - Может сжимать (gzip)
   │
   ▼
9. Nginx отправляет ответ клиенту
   HTTP/1.1 200 OK
   Content-Encoding: gzip
   {"users": [...]}
```

## 9. Сравнение методов балансировки

### Таблица сравнения

| Метод | Когда использовать | Преимущества | Недостатки |
|-------|-------------------|--------------|------------|
| **Round Robin** | Все серверы одинаковые | Простота, равномерность | Не учитывает нагрузку |
| **Weighted** | Серверы разной мощности | Гибкость распределения | Нужно правильно настроить веса |
| **Least Connections** | Разное время обработки | Более равномерная нагрузка | Требует отслеживания соединений |
| **IP Hash** | Нужна привязка сессий | Гарантированная привязка | Проблемы при падении сервера |

## 10. Типичные сценарии использования

### Сценарий 1: Одно приложение, один сервер

```
Клиент → Nginx (SSL, статика) → FastAPI (8000)
```

**Конфигурация:** Простой reverse proxy

### Сценарий 2: Одно приложение, несколько серверов

```
Клиент → Nginx (Load Balancer) → [FastAPI 1, FastAPI 2, FastAPI 3]
```

**Конфигурация:** Load balancing с health checks

### Сценарий 3: Микросервисы

```
Клиент → Nginx → /api/users → User Service
              → /api/orders → Order Service
              → /api/payments → Payment Service
```

**Конфигурация:** Разные location блоки для разных сервисов

### Сценарий 4: Высокая нагрузка

```
Клиент → Nginx (кэш, сжатие) → Load Balancer → [App 1, App 2, App 3]
```

**Конфигурация:** Кэширование + Load balancing + Сжатие

## 11. Ключевые концепции - Шпаргалка

### Reverse Proxy
- **Что:** Nginx принимает запросы и перенаправляет их на backend
- **Зачем:** Скрытие структуры, SSL, оптимизация
- **Директива:** `proxy_pass`

### Load Balancing
- **Что:** Распределение запросов между несколькими серверами
- **Зачем:** Масштабирование, отказоустойчивость
- **Директива:** `upstream` + `proxy_pass`

### Health Checks
- **Что:** Автоматическое исключение упавших серверов
- **Зачем:** Отказоустойчивость
- **Директива:** `max_fails`, `fail_timeout`

### Backup сервер
- **Что:** Резервный сервер, используемый при падении основных
- **Зачем:** Гарантия доступности
- **Директива:** `backup` в upstream

### SSL/TLS терминация
- **Что:** Nginx обрабатывает HTTPS, backend работает по HTTP
- **Зачем:** Упрощение, производительность
- **Директива:** `ssl_certificate`, `ssl_certificate_key`

## 12. Визуализация конфигурации

### Структура конфигурационного файла

```
nginx.conf
│
├── upstream backend {          ← Определение группы серверов
│     server 127.0.0.1:8000;
│     server 127.0.0.1:8001;
│   }
│
└── server {                   ← Виртуальный хост
      listen 80;
      server_name example.com;
      │
      ├── location /static/ {   ← Правило для статики
      │     alias /var/www/static/;
      │   }
      │
      └── location / {         ← Правило для API
            proxy_pass http://backend;
          }
    }
```

### Порядок обработки запроса

```
1. Nginx получает запрос
   │
   ▼
2. Проверяет server_name
   (какой виртуальный хост)
   │
   ▼
3. Ищет подходящий location
   (самый специфичный)
   │
   ▼
4. Если proxy_pass → выбирает сервер из upstream
   │
   ▼
5. Проксирует запрос
   │
   ▼
6. Получает ответ
   │
   ▼
7. Обрабатывает ответ
   (кэш, сжатие)
   │
   ▼
8. Отправляет клиенту
```

## Резюме

### Основные концепции

1. **Reverse Proxy** = Nginx принимает запросы и перенаправляет их
2. **Load Balancing** = Распределение между несколькими серверами
3. **Health Checks** = Автоматическое исключение упавших серверов
4. **Backup** = Резервный сервер на случай падения основных

### Ключевые директивы

- `upstream` - группа серверов
- `proxy_pass` - проксирование запросов
- `location` - правила для разных путей
- `server` - виртуальный хост

### Когда что использовать

- **Один сервер** → Reverse Proxy
- **Несколько серверов** → Load Balancing
- **Разная мощность** → Weighted
- **Разное время обработки** → Least Connections
- **Нужны сессии** → IP Hash
